= 在 NetApp Disaster Recovery 中优化复制计划
:hardbreaks:
:allow-uri-read: 
:icons: font
:imagesdir: ../media/use/


[role="lead"]
复制计划是灾难恢复策略的重要组成部分，它定义了快照频率、引导顺序、网络映射以及故障转移和故障恢复的其他关键详细信息。在 NetApp Disaster Recovery 中创建复制计划之前，请确保您了解复制计划的工作方式和最佳实践。



[[about-replication-plans]]
== 关于复制计划

您可以使用单个复制计划保护多个虚拟机、数据存储或命名空间。灾难恢复会为所有托管受保护数据资源的 ONTAP 卷创建 ONTAP 一致性组。



[[resource-planning]]
== 资源规划

在将资源分配给复制计划之前组织您的 VM 或命名空间，以最大限度地减少蔓延。将需要保护的资源放置在数据存储的子集上，并将不会受保护的资源放置在不同的数据存储子集上。若要在创建复制计划之前组织资源组，请参阅link:resource-group.html["创建资源组"]。



[[test-failover]]
== 测试故障转移

创建复制计划时，您可以选择配置唯一的测试故障转移映射。

如果您计划将执行测试故障转移作为复制计划的一部分，则应提供一组测试故障转移映射，以确保在故障转移测试期间启动的 VM 不会干扰生产 VM。您可以通过为测试 VM 提供不同的 IP 地址，或者将测试 VM 的虚拟 NIC 映射到与生产环境隔离但具有相同 IP 配置的不同网络（称为 _bubble_ 或 _test network_）来实现这一点。



[[snapshots]]
== Snapshot

灾难恢复在源集群和目标集群上维护相同数量的快照。默认情况下，该服务每 24 小时执行一次快照协调过程，以确保源集群和目标集群上的快照数量相同。

以下情况可能会导致源集群和目标集群之间的快照数量不同：

* 某些情况可能会导致灾难恢复之外的ONTAP操作在卷中添加或删除快照：
+
** 如果源站点上缺少快照，则目标站点上的相应快照可能会被删除，具体取决于关系的默认SnapMirror策略。
** 如果目标站点上缺少快照，则服务可能会在下一个计划快照协调过程中删除源站点上的相应快照，具体取决于关系的默认 SnapMirror 策略。


* 复制计划的快照保留计数的减少可能导致服务删除源站点和目标站点上最旧的快照以满足新减少的保留数量。


在这些情况下，灾难恢复会在下一次一致性检查时从源和目标集群中删除较旧的快照。或者，管理员可以通过选择“操作”立即执行快照清理image:icon-horizontal-dots.png["水平点操作菜单"]复制计划上的图标并选择*清理快照*。

灾难恢复每 24 小时执行一次快照对称性检查。



[[platform-managed-backups]]
== 平台管理的备份

如果您计划使用平台管理的备份（即 ONTAP 管理的快照），建议您使用 *MirrorAll* 复制策略。查看表格，了解不同 SnapMirror 复制策略的影响以及为何 MirrorAll 是推荐选项。

[cols="10,10,80"]
|===


| 策略 | 建议 | 笔记 


| *MirrorAll* | 建议 | 不要将 SnapMirror 传输快照用于故障转移或故障恢复操作。 


| *MirrorVault* .2+| 备选建议 .2+| 确保在故障切换或故障回复期间选择的快照同时存在于源卷和目标卷上。否则将导致错误："转换到 'snapmirrored' 状态失败。原因：未找到通用快照。"不要将 SnapMirror 传输快照用于故障转移或故障恢复操作。 


| *异步* 


| *MirrorLatest* | 不推荐 | 此策略导致目标实际上只有一个用于故障转移的常见快照，这对于灾难恢复方案来说并不理想。 
|===


[[disaster-recovery-managed-backups]]
== 灾难恢复管理的备份

使用 Disaster Recovery 托管备份时，以下指南适用于在 NetApp Disaster Recovery 之外创建的 SnapMirror 关系：

* SnapMirror 关系可以支持 MirrorAll、MirrorVault、MirrorLatest 和异步复制策略。
* 请勿为这些关系安排更新，因为它们将由 Disaster Recovery 服务管理。




[[application-consistent-replicas]]
== 应用程序一致性副本

许多虚拟机托管数据库服务器，例如 Oracle 或 Microsoft SQL Server。这些数据库服务器需要应用程序一致的快照，以确保在拍摄快照时数据库处于一致状态。

应用程序一致性快照可确保在拍摄快照时数据库处于一致状态。这很重要，因为它可以确保数据库在故障转移或故障回复操作后能够恢复到一致状态。

由数据库服务器管理的数据可能与托管数据库服务器的虚拟机在同一数据存储区上，或者可能在不同的数据存储区上。下表显示了 NetApp Disaster Recovery 中应用程序一致性快照的支持配置：

[cols="20,20,40a"]
|===
| 数据位置 | 支持 | 笔记 


| 与虚拟机位于同一 vCenter 数据存储区内 | 是  a| 
由于数据库服务器和数据库都位于同一个数据存储区中，因此在故障转移时服务器和数据都将同步。



| 与虚拟机位于不同的 vCenter 数据存储区内 | 否  a| 
灾难恢复无法识别数据库服务器的数据何时位于不同的 vCenter 数据存储上。该服务无法复制数据，但可以复制数据库服务器虚拟机。

虽然数据库数据无法复制，但该服务可确保数据库服务器执行所有必要步骤，以确保数据库在 VM 备份时处于静止状态。



| 在外部数据源中 | 否  a| 
如果数据驻留在客户机安装的 LUN 或 NFS 共享上，灾难恢复无法复制数据，但可以复制数据库服务器 VM。

虽然数据库数据无法复制，但该服务可确保数据库服务器执行所有必要步骤，以确保数据库在 VM 备份时处于静止状态。

|===
在计划备份期间，灾难恢复会使数据库服务器处于静止状态，然后对托管数据库服务器的虚拟机进行快照。这可确保在拍摄快照时数据库处于一致状态。

* 对于 Windows VM，该服务使用 Microsoft 卷影复制服务 (VSS) 与任一数据库服务器类型进行协调。
* 对于 Linux VM，该服务使用一组脚本将 Oracle 服务器置于备份模式。
